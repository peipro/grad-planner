## 一、里程碑"变成 5 份相同"问题的根因分析

### 结论：删除里程碑本身是安全的，真正的元凶是 `updateMilestone` 按 `id` 匹配时未防 `undefined`

**直接触发链**：

1. 里程碑数据在某次导入/恢复/旧版本迁移中丢失了 `id`（`JSON.stringify` 会直接丢弃 `undefined` 字段，所以存成"无 id 的里程碑"）。
2. 此后任何一次**编辑/勾选检查点/撤销删除项目**都会调用 `updateMilestone(m)`：
   ```js
   updateMilestone: (m) => set((s) => ({ milestones: s.milestones.map((x) => (x.id === m.id ? m : x)) }))
   ```
   当 `m.id === undefined` 时，`x.id === undefined` 会匹配**所有无 id 的里程碑**，把整份列表全部替换成正在编辑的那一条 → 出现 N 份完全相同的内容。
3. 同理 `deleteMilestone(undefined)` 会误删所有无 id 的里程碑。

**你回忆的"删除里程碑"**：在 id 完好的情况下，`deleteMilestone(id)` 只是过滤掉一条，不会复制、不会丢 id，是安全的。真正危险的步骤是删除之后又对某条里程碑做了编辑/勾选——如果那时 id 已经损坏，就会触发上面的批量复制。

### 已做的修复（三重防护）
| 修复 | 位置 |
|---|---|
| ✅ 载入时自愈：去重 + 补齐缺失 id + 过滤无效检查点 | `store.ts` `repairMilestones`（已接入 persist `merge`） |
| ✅ `updateMilestone`/`deleteMilestone` 在无 id 时直接 no-op，不再误伤 | `store.ts` |
| ✅ 导入/恢复备份时统一走 `repairMilestones` | `SettingsView.tsx` |

## 四、剩余风险与建议（未改动，需知晓/决策）

### ⚠️ 安全
1. **局域网明文 HTTP**：token 走 query、数据明文传输，同网段可被嗅探。个人局域网可接受；介意可后续加 HTTPS 或 WebSocket+HMAC。
2. **X API 密钥**：已用 `safeStorage` 加密落盘（良好）；但 `newsConfig` 对象在内存中若含密钥会有被 `exportData` 导出的风险——已确认 store 中 `xKey/xSecret` 恒为空串，安全。
3. **资讯正文提取**：`extractArticleText` 用正则剥标签，可能有漏网（如 `<img>` 内联事件）；但正文以 React 文本渲染（自动转义），无 XSS。

### 🟡 数据一致性与健壮性
4. **双端并发写无冲突解决**：桌面/平板同时编辑=最后写入者覆盖。个人工具可接受。
5. **无数据迁移/版本化**：persist `version:0`，未来改 schema 无迁移通道。建议需要时加 `version` + `migrate`。
6. **`uid()` 碰撞**：`Math.random().toString(36) + Date.now().toString(36)`，同毫秒极低概率碰撞；高频循环创建时建议改用递增序号或 `crypto.randomUUID()`。
7. **`exportData` 导出完整 state（含 pomo 运行态）**：恢复时 pomo 不覆盖，影响小。

### 🟡 功能完整性
8. **`resetAll` 清空 `paperStages`**：清空后文献阶段列表也被清掉（需重新建）。建议保留默认阶段。
9. **删除无统一撤销**：待办/项目有撤销，里程碑/笔记/文献/日程无。建议统一回收站或撤销。
10. **任务/习惯无提醒**：提醒仅覆盖日历事件与生日。建议补任务到期提醒、习惯打卡提醒。
11. **黄历功能过重**：显著增大 bundle，与主线弱相关，建议折叠为可选项。

### 🟡 工程
12. **无 TypeScript 于主进程**：`electron/*.cjs` 为纯 JS，缺类型保障。
13. **electron-builder 偶发失败**：npx 缓存下 `validateConfig`/签名偶发报错，重试即可；建议固定 electron-builder 版本或改用项目内 `npm run dist`（本地 node_modules）。
